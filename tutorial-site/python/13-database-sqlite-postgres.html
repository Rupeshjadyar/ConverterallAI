🗣️ How to Speak in an Interview (Crisp Speaking Points)
  • What is PEP 249 (Python DB-API 2.0)? The standard specification that all Python database drivers (sqlite3, psycopg2, mysqlclient) must implement, providing uniform methods: connect(), cursor(), execute(), fetchall(), commit(), and rollback().
  • How to prevent SQL Injection in Python? NEVER use f-strings or string concatenation to build SQL queries! Always pass query parameters as a tuple/list to cursor.execute(sql, (param1, param2)) so the driver quotes and escapes them safely.
  • What is Connection Pooling? Opening a TCP connection, performing TLS handshakes, and authenticating with PostgreSQL on every HTTP request adds 50-100ms latency. A connection pool keeps a pool of warm connections ready in memory to be reused by worker threads.
  • fetchone() vs fetchall() vs fetchmany(size): fetchall() loads the ENTIRE result set into RAM (dangerous for millions of rows!). Use fetchmany(1000) or iterate over the cursor directly to stream rows in batches.
  • Raw SQL vs ORM: Raw SQL offers maximum performance and explicit query control. ORMs (SQLAlchemy, Django ORM) offer rapid development, type safety, database portability, and eliminate boilerplate mapping.

1. The Python DB-API 2.0 (PEP 249) Standard

In Python, every database adapter follows the universal PEP 249 standard. Whether you are querying SQLite, PostgreSQL, MySQL, or Oracle, the programming workflow is identical:

1. connection = db_driver.connect(...)
2. cursor = connection.cursor()
3. cursor.execute(query, params)
4. results = cursor.fetchall()
5. connection.commit() & connection.close()

2. Embedded Persistence with sqlite3

Python includes sqlite3 directly in its standard library — zero installation required. SQLite is an in-process, serverless relational database engine stored in a single file on disk (or in RAM with :memory:).

It is ideal for desktop applications, testing, edge devices, and prototyping before moving to PostgreSQL.

3. The Critical Danger of SQL Injection

Never write: cursor.execute(f'SELECT * FROM users WHERE email = "{user_input}"'). If an attacker inputs ' OR '1'='1, they bypass authentication entirely and expose every user's data!

Always write: cursor.execute('SELECT * FROM users WHERE email = ?', (user_input,)). The driver safely passes parameters separately from the SQL statement.

Code Example 1: Complete CRUD Workflow with Built-in sqlite3

python
import sqlite3

# 1. Connect to local database file (creates it if missing)
conn = sqlite3.connect('local_academy.db')
cursor = conn.cursor()

# 2. Create table schema
cursor.execute('''
    CREATE TABLE IF NOT EXISTS students (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        name TEXT NOT NULL,
        track TEXT NOT NULL,
        gpa REAL DEFAULT 0.0
    )
''')

# 3. Parameterized INSERT (Safe against SQL Injection!)
new_students = [
    ('Aarav Sharma', 'Full-Stack Python', 3.9),
    ('Priya Verma', 'AI & Machine Learning', 4.0),
    ('Rohan Patel', 'Cloud Architecture', 3.7)
]
cursor.executemany('''
    INSERT INTO students (name, track, gpa) VALUES (?, ?, ?)
''', new_students)
conn.commit()  # Save changes permanently!

# 4. Query and iterate through rows
cursor.execute('SELECT id, name, track, gpa FROM students WHERE gpa >= ?', (3.8,))
for row in cursor.fetchall():
    print(f'Honor Student: {row[1]} ({row[2]}) - GPA: {row[3]}')

conn.close()
• cursor.executemany() batches multiple insertions in a single transaction for high performance.

Code Example 2: SQL Injection Demonstration: The Hack vs The Safe Fix

python
import sqlite3
conn = sqlite3.connect(':memory:')
cur = conn.cursor()
cur.execute('CREATE TABLE secrets (id INT, api_key TEXT)')
cur.execute("INSERT INTO secrets VALUES (1, 'sk_live_super_secret_key')")
conn.commit()

# Malicious attacker input
malicious_user_id = '1 OR 1=1'

# VULNERABLE CODE (Never do this!):
# cur.execute(f'SELECT * FROM secrets WHERE id = {malicious_user_id}')  <-- Leaks all keys!

# SAFE PARAMETERIZED CODE:
cur.execute('SELECT * FROM secrets WHERE id = ?', (malicious_user_id,))
results = cur.fetchall()
print(f'Safe query results: {results}')  # Empty list [] - Attack completely neutralized!
• Parameterized queries prevent attacker payloads from being parsed as SQL code.

Code Example 5: Using sqlite3 with Row Factory for Named Column Access

python
import sqlite3

conn = sqlite3.connect(':memory:')
# Row factory allows dict-like and index-like access: row['name'] or row[0]
conn.row_factory = sqlite3.Row
cur = conn.cursor()

cur.execute('CREATE TABLE items (id INT, name TEXT)')
cur.execute("INSERT INTO items VALUES (1, 'Laser Mouse')")
conn.commit()

cur.execute('SELECT * FROM items WHERE id = 1')
row = cur.fetchone()
print(f'Item by name: {row["name"]}, Item by index: {row[1]}')
• sqlite3.Row provides named access without the overhead of converting rows into full dictionaries.

Code Example 6: Transaction Context Management (Automatic Rollback on Exception)

python
import sqlite3

conn = sqlite3.connect(':memory:')
cur = conn.cursor()
cur.execute('CREATE TABLE accounts (id INT PRIMARY KEY, balance REAL)')
cur.execute('INSERT INTO accounts VALUES (1, 1000.0), (2, 500.0)')
conn.commit()

# Using connection as a context manager automatically handles COMMIT / ROLLBACK!
try:
    with conn:
        cur.execute('UPDATE accounts SET balance = balance - 200 WHERE id = 1')
        # Simulate crash
        raise RuntimeError('Network timeout during bank transfer!')
        cur.execute('UPDATE accounts SET balance = balance + 200 WHERE id = 2')
except RuntimeError as err:
    print(f'Transaction safely rolled back due to: {err}')

cur.execute('SELECT balance FROM accounts WHERE id = 1')
print(f'Account 1 balance is intact: ${cur.fetchone()[0]:.2f}')
• with conn: automatically issues a ROLLBACK if any exception escapes the block, preserving data integrity.

⚠️ Common Beginner & Production Mistakes
  • Using f-strings for SQL queries: The #1 security flaw in web development. Always pass query parameters as second argument to execute().
  • Forgetting conn.commit(): In Python DB-API, transactions are open by default. If you omit conn.commit(), your INSERT and UPDATE statements are never written to disk!
  • Calling fetchall() on massive tables: Trying to load 10 million rows into memory crashes server RAM with an Out Of Memory (OOM) error. Use fetchmany() or stream via cursor iteration.
💡 Senior Python Engineer Pro Tips
  • Always use connection pools in web servers: In FastAPI or Flask, use SQLAlchemy's QueuePool or asyncpg.create_pool() to reuse database connections across concurrent web worker threads.
  • Use Alembic for database migrations: Never run manual ALTER TABLE commands in production. Use Alembic (from SQLAlchemy) to version control your database schema alongside your Git commits!
⚑ Quick Recap & Key Takeaways
  • PEP 249 DB-API 2.0 defines uniform database APIs across SQLite, PostgreSQL, and MySQL.
  • Never use string formatting in SQL; use parameterized queries (?, %s) to prevent SQL injection.
  • sqlite3 is built into Python; psycopg2 connects to enterprise PostgreSQL.
  • Always call conn.commit() to persist transactions permanently.
  • SQLAlchemy ORM bridges relational tables and Python OOP classes.

def transfer_funds(conn, from_acc, to_acc, amount):
    cur = conn.cursor()
    with conn:
        cur.execute('SELECT balance FROM accounts WHERE id = ?', (from_acc,))
        bal = cur.fetchone()[0]
        if bal < amount:
            raise ValueError('Insufficient funds')
        cur.execute('UPDATE accounts SET balance = balance - ? WHERE id = ?', (amount, from_acc))
        cur.execute('UPDATE accounts SET balance = balance + ? WHERE id = ?', (amount, to_acc))
    print('Transfer completed successfully.')
