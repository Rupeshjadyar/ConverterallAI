1. The `try...catch...finally` Anatomy

The try block encloses code that might encounter runtime failures (such as parsing invalid JSON or network requests):

Code Example 1: Basic Try-Catch-Finally Structure

javascript
function parseUserData(jsonString) {
  let spinnerActive = true;
  console.log("Loading spinner activated.");

  try {
    // 1. Risky code executed inside 'try'
    const user = JSON.parse(jsonString); // Might throw SyntaxError!
    console.log("Parsed user successfully:", user.name);
    return user;
  } catch (error) {
    // 2. 'catch' runs ONLY if an exception occurs in 'try'
    console.error(`Parsing Failed: ${error.message}`);
    return null; // Graceful fallback!
  } finally {
    // 3. 'finally' ALWAYS executes, whether there was an error or not!
    spinnerActive = false;
    console.log("Cleanup completed: Loading spinner deactivated.");
  }
}

parseUserData('{"name": "Alice"}'); // Success!
parseUserData("INVALID_RAW_STRING"); // Handled safely without crashing the page!

2. Standard Built-in Error Types

JavaScript includes specific built-in Error subclasses to categorize different failure scenarios:

Error Type Cause of Error Example
TypeError Value is not of the expected type or null method called null.toUpperCase()
ReferenceError Attempting to read an undeclared variable console.log(undeclaredVar)
SyntaxError Invalid language grammar (e.g. malformed JSON) JSON.parse("{ bad json }")
RangeError Number falls outside allowed numeric bounds new Array(-1)

3. Throwing Explicit Errors

Use the throw keyword to halt execution when business rules or parameters are violated:

Code Example 2: Validating Inputs with `throw`

javascript
function withdrawFunds(accountBalance, amount) {
  if (typeof amount !== "number" || Number.isNaN(amount)) {
    throw new TypeError("Withdrawal amount must be a valid number.");
  }
  if (amount <= 0) {
    throw new RangeError("Withdrawal amount must be greater than zero.");
  }
  if (amount > accountBalance) {
    throw new Error("Insufficient funds for requested transaction.");
  }

  return accountBalance - amount;
}

try {
  const newBalance = withdrawFunds(500, 700);
} catch (err) {
  console.warn(`Transaction Warning [${err.name}]: ${err.message}`);
}

4. Architecting Custom Error Classes

In large enterprise systems, you should create specialized custom error classes extending the base Error class:

Code Example 3: Subclassing Custom Domain Errors

javascript
class ValidationError extends Error {
  constructor(message, fieldName) {
    super(message); // Pass message to standard Error constructor
    this.name = "ValidationError";
    this.fieldName = fieldName;
  }
}

class NetworkTimeoutError extends Error {
  constructor(url, timeoutMs) {
    super(`Request to ${url} timed out after ${timeoutMs}ms`);
    this.name = "NetworkTimeoutError";
  }
}

// Handling specialized errors selectively:
try {
  throw new ValidationError("Email address must contain an '@' symbol.", "email");
} catch (error) {
  if (error instanceof ValidationError) {
    console.error(`Form Field '${error.fieldName}' is invalid: ${error.message}`);
  } else {
    console.error("Unknown system error occurred:", error);
  }
}

5. The Asynchronous Error Catching Pitfall

A common beginner mistake is wrapping an asynchronous timer or promise in a synchronous try/catch block:

Code Example 4: Asynchronous Try-Catch Trap

javascript
// THE BUG: Synchronous try/catch finishes before setTimeout runs!
try {
  setTimeout(() => {
    // throw new Error("Boom!"); // UNCAUGHT CRASH! try/catch has already exited!
  }, 100);
} catch (err) {
  console.log("Will NEVER catch the error here!");
}

// THE FIX: Place try/catch INSIDE the asynchronous callback:
setTimeout(() => {
  try {
    throw new Error("Caught safely inside callback!");
  } catch (err) {
    console.log("Successfully handled:", err.message);
  }
}, 100);

⚠ Common Beginner Mistakes
  • Empty catch (e) {} blocks: Silently swallowing errors with an empty catch block is considered one of the worst coding antipatterns. It turns fatal bugs into invisible phantom defects! Always log or report caught errors.
  • Throwing plain strings: Writing throw "Invalid input"; is bad practice because strings lack stack traces and error types! Always throw an instance of Error: throw new Error("Invalid input");.
  • Overusing try/catch for standard logic: Do not use try/catch for simple null checks (e.g. if (!user)). try/catch carries a slight optimization cost; reserve it for genuine exceptions and external I/O.
💡 Pro Tips from Senior Engineers
  • Global unhandled error traps: Use window.addEventListener("error", (e) => { ... }) and window.addEventListener("unhandledrejection", (e) => { ... }) to catch any error that slips through and log it to telemetry.
  • Error Cause (ES2022): You can chain error causes: throw new Error("Payment failed", { cause: originalNetworkError });!
  • Always clean up in finally: Whether downloading finishes or fails, put loading state dismissal (e.g. hideSpinner()) in finally so users never get stuck staring at an infinite loading bar.
⚡ Quick Recap
  • try...catch prevents uncaught exceptions from terminating program execution.
  • The finally block executes unconditionally for guaranteed resource cleanup.
  • Always throw instances of Error, not raw strings.
  • Inspect err.name, err.message, and err.stack for diagnosis.
  • Subclass Error to create specialized domain exceptions like ValidationError.
  • Synchronous try/catch cannot catch errors inside asynchronous callbacks.

7. Practice Coding Exercises

Exercise 1 (Easy): Throw a RangeError Easy

Write an if check inside a function setVolume(level) that throws a RangeError with message "Volume must be between 0 and 100" if level < 0 || level > 100.

Hint: throw new RangeError("...");
Solution:
if (level < 0 || level > 100) {
  throw new RangeError("Volume must be between 0 and 100");
}
Exercise 2 (Medium): Safe JSON Parser Helper Medium

Write a function safeJsonParse(text, fallback = {}) that attempts to parse text with JSON.parse, but returns fallback if parsing throws an error.

Hint: try { return JSON.parse(text); } catch { return fallback; }
Solution:
function safeJsonParse(text, fallback = {}) {
  try {
    return JSON.parse(text);
  } catch (err) {
    return fallback;
  }
}
Exercise 3 (Hard): Custom HttpError Class Hard

Create a custom class HttpError extending Error that accepts statusCode and statusText, setting this.statusCode = statusCode and this.name = "HttpError".

Hint: class HttpError extends Error { constructor(status, text) { super(text); ... } }
Solution:
class HttpError extends Error {
  constructor(statusCode, statusText) {
    super(`HTTP ${statusCode}: ${statusText}`);
    this.name = "HttpError";
    this.statusCode = statusCode;
  }
}
