1. The Single Thread & The Event Loop

JavaScript is strictly single-threaded — it possesses only one Call Stack and can execute only one instruction at a single moment in time. If you run a loop that computes prime numbers for 10 seconds, the browser tab freezes completely: buttons cannot be clicked, text cannot be selected, and animations stall. JavaScript single-threaded hai — iska ek hi Call Stack hota hai jo ek samay me ek hi command run kar sakta hai. Browser ko freeze hone se bachane ke liye Event Loop aur asynchronous architecture use hota hai.

To handle long-running operations like timers, network requests, disk I/O, or user interactions, the browser environment provides Web APIs (external C++ worker threads). When an asynchronous operation finishes, its callback is placed into a waiting queue. The Event Loop continuously monitors the Call Stack: the instant the Call Stack becomes empty, it pushes the next waiting queued callback onto the stack to execute. Browser ke Web APIs background me network ya timer handle karte hain. Jab background kaam poora hota hai, Event Loop callback ko Call Stack me daalta hai jab stack khali ho.

JavaScript — Synchronous vs Asynchronous Execution Order 
console.log("1: Synchronous start");

// Web API timer: scheduled in background
setTimeout(function() {
  console.log("2: Inside setTimeout callback (Macro-task)");
}, 0); // Notice: Even with 0ms delay!

// Microtask: Higher priority than setTimeout
Promise.resolve().then(function() {
  console.log("3: Inside Promise microtask");
});

console.log("4: Synchronous end");

/* Output Console Order:
   1: Synchronous start
   4: Synchronous end
   3: Inside Promise microtask
   2: Inside setTimeout callback (Macro-task)
*/
Line-by-Line Execution Analysis:
  • Lines 1 & 12: Synchronous statements run immediately on the Call Stack.
  • Lines 4-6: setTimeout(..., 0) registers with the browser Web API timer thread, then dispatches its callback to the Macrotask Queue.
  • Lines 9-11: Resolved promises dispatch their callbacks to the high-priority Microtask Queue.
  • The Rule: The Event Loop clears ALL microtasks before running ANY macrotask! Hence output order is 1 → 4 → 3 → 2.

2. Callback Hell: The Pyramid of Doom

Before ES2015 (ES6) introduced native Promises, developers handled asynchronous sequences using nested callbacks. When operation B depended on operation A, and operation C depended on B, the indentation nested deeper and deeper into an unmaintainable triangular monstrosity nicknamed the "Pyramid of Doom". Promises se pehle callbacks ko ek dusre ke andar nest kiya jata tha. Isse code aage badhta rehta tha jise "Callback Hell" ya "Pyramid of Doom" kehte hain jisme error handling bohot mushkil hoti hai.

JavaScript — The Legacy Nightmare: Callback Hell 
// BAD PRACTICE: Callback Hell (Nested callbacks)
getUserProfile(userId, function(err, user) {
  if (err) {
    handleError(err);
  } else {
    getUserOrders(user.id, function(err, orders) {
      if (err) {
        handleError(err);
      } else {
        getOrderInvoice(orders[0].id, function(err, invoice) {
          if (err) {
            handleError(err);
          } else {
            sendInvoiceEmail(user.email, invoice, function(err, success) {
              if (err) handleError(err);
              else console.log("Invoice emailed successfully!");
            });
          }
        });
      }
    });
  }
});

3. Anatomy of a Promise

A Promise is a first-class JavaScript object representing the eventual completion (or failure) of an asynchronous operation and its resulting value. A promise exists in one of three distinct states: Promise ek special JavaScript object hai jo future me complete hone wale kisi operation ka result represent karta hai. Iske 3 states hote hain:

Promise State Meaning Transition Capability
pending Initial state. The operation is still in progress (buzzer in hand). Can transition to fulfilled or rejected.
fulfilled The operation completed successfully. Has a resolved value. Settled permanently. Cannot change state ever again.
rejected The operation failed. Contains an error reason. Settled permanently. Cannot change state ever again.
JavaScript — Creating and Consuming a Promise 
// Simulating an asynchronous database query
function fetchUserFromDB(userId) {
  return new Promise(function(resolve, reject) {
    console.log("[DB] Querying database for user ID:", userId);

    setTimeout(function() {
      if (userId === 42) {
        // Success: Transition state to 'fulfilled'
        resolve({ id: 42, username: "dev_priya", plan: "pro" });
      } else {
        // Failure: Transition state to 'rejected'
        reject(new Error("User with ID " + userId + " was not found."));
      }
    }, 1000);
  });
}

// Consuming the promise with .then(), .catch(), and .finally()
fetchUserFromDB(42)
  .then(function(user) {
    console.log("Success! Welcome back,", user.username);
    return user.plan; // Returns a new chained promise!
  })
  .then(function(planName) {
    console.log("Active membership plan tier:", planName);
  })
  .catch(function(err) {
    console.error("Query failed:", err.message);
  })
  .finally(function() {
    console.log("Database transaction closed.");
  });
Key Architecture Rules:
  • new Promise((resolve, reject) => { ... }) takes an "executor" function that runs synchronously right away.
  • Calling resolve(value) marks it fulfilled. Calling reject(error) marks it rejected.
  • Every .then() callback automatically returns a new promise. If you return a primitive value, it resolves instantly to that value; if you return another promise, it awaits that promise before continuing down the chain!
  • A single .catch() at the end catches any rejection thrown at ANY prior step in the entire chain.

4. Promise Combinators: Parallel Asynchronous Execution

When you have multiple asynchronous jobs that do not depend on each other (e.g. fetching user data, loading notifications, and fetching weather), running them sequentially is wasteful. ES6+ offers four powerful concurrency methods on the Promise constructor: Agar aapko multiple independent background tasks ek saath run karne hain, toh Promise ke parallel methods use karein jaise Promise.all aur Promise.allSettled:

JavaScript — Promise.all() vs Promise.allSettled() 
const task1 = new Promise(resolve => setTimeout(() => resolve("Profile loaded"), 500));
const task2 = new Promise(resolve => setTimeout(() => resolve("Cart items (3)"), 300));
const task3 = new Promise((_, reject) => setTimeout(() => reject(new Error("Ads blocked")), 200));

// 1. Promise.all() — "All or nothing" (Rejects immediately if ANY promise fails)
Promise.all([task1, task2])
  .then(results => console.log("All passed:", results)) // ['Profile loaded', 'Cart items (3)']
  .catch(err => console.error("One failed:", err));

// 2. Promise.allSettled() — Never fails! Waits for all to either fulfill or reject
Promise.allSettled([task1, task2, task3])
  .then(reports => {
    reports.forEach(report => {
      if (report.status === "fulfilled") {
        console.log("Success value:", report.value);
      } else {
        console.warn("Failed reason:", report.reason.message);
      }
    });
  });

// 3. Promise.race() — Settles as soon as the FASTEST promise settles (wins or fails)
// 4. Promise.any() — Resolves as soon as ANY promise fulfills (ignores rejections until all fail)

5. Modern Asynchronous Code with async & await

Introduced in ES2017, async and await is syntactic sugar built directly on top of Promises. It allows you to write non-blocking asynchronous logic with the natural clarity and visual structure of synchronous, line-by-line code. async aur await Promises ke upar banaya gaya modern syntax hai. Isse asynchronous code bilkul regular synchronous code ki tarah seedha aur aasan dikhta hai bina lambi .then() chains ke.

  • async keyword: Put in front of any function declaration or arrow function. It guarantees that the function always returns a Promise. If you return "hello", JS automatically wraps it in Promise.resolve("hello").
  • await keyword: Can only be placed inside an async function. It pauses the function execution until the promised value resolves (or rejects), without freezing the main browser thread!
JavaScript — Clean async/await with try...catch 
// Helper that returns a promise after a delay
const sleep = (ms) => new Promise(resolve => setTimeout(resolve, ms));

async function renderUserDashboard(userId) {
  try {
    console.log("Step 1: Connecting to cloud server...");
    await sleep(800); // Wait 800ms non-blockingly

    console.log("Step 2: Authenticating user #" + userId);
    await sleep(600);

    const user = { id: userId, name: "Aarav Sharma", role: "Software Architect" };
    console.log("Step 3: User verified successfully:", user.name);

    return user;
  } catch (error) {
    console.error("Dashboard error intercepted:", error.message);
    throw error; // Re-throw if caller needs to handle
  } finally {
    console.log("Step 4: Cleanup & Hide loading spinner.");
  }
}

// Invoking an async function (it returns a promise!)
renderUserDashboard(101).then(user => console.log("Final callback:", user));

⚠ Common Beginner Pitfalls
  • Forgetting to return inside .then(): If you don't return a value or promise from inside a .then() block, the next .then() in the chain receives undefined.
  • The "Async in forEach" Trap: array.forEach(async (item) => { await doSomething(); }) does NOT pause the loop! forEach executes all async callbacks concurrently without waiting. Use a standard for (const item of array) loop or Promise.all(array.map(...)) instead.
  • Uncaught Rejections: Forgetting a .catch() on a promise or omitting try...catch around await causes an unhandled promise rejection error that crashes modern node scripts or pollutes browser consoles.
  • Creating Redundant Promises: Wrapping a function that already returns a promise inside new Promise((res, rej) => ...) is an antipattern known as the "Promise constructor antipattern". Just return the original promise directly!
💡 Senior Pro Tips
  • Parallelize Independent Awaits: Never do const u = await getUser(); const p = await getPosts(); if posts don't depend on user! Do const [u, p] = await Promise.all([getUser(), getPosts()]); to cut network waiting time in half.
  • Top-Level Await: In modern JavaScript ES Modules (<script type="module">), you can write await directly in the root of the file without wrapping it in an async function.
✅ Quick Recap
  • JavaScript is single-threaded; asynchronous tasks run off-thread via Web APIs.
  • Microtasks (Promises) always run before Macrotasks (setTimeout, setInterval).
  • A Promise has 3 states: pending, fulfilled, and rejected.
  • async functions always return a Promise automatically.
  • await pauses execution of the async function until the promise settles.
  • Always protect await statements with try...catch...finally blocks.

function delay(milliseconds) {

Exercise 3: Promise Timeout Wrapper

Write a higher-order function withTimeout(promise, timeoutMs) that uses Promise.race(). If the given promise does not settle before timeoutMs, reject with new Error("Operation timed out!").

View Solution 
function withTimeout(promise, timeoutMs) {
  const timeoutPromise = new Promise((_, reject) => {
    setTimeout(() => {
      reject(new Error("Operation timed out after " + timeoutMs + "ms!"));
    }, timeoutMs);
  });

  return Promise.race([promise, timeoutPromise]);
}

// Test with a slow job (3000ms) and 1000ms limit:
const slowJob = new Promise(res => setTimeout(() => res("Finished!"), 3000));

withTimeout(slowJob, 1000)
  .then(data => console.log(data))
  .catch(err => console.error(err.message)); // Logs: "Operation timed out after 1000ms!"
