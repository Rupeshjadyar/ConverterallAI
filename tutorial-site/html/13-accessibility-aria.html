1. The Four Principles of WCAG (POUR)

The internationally recognized standard for digital accessibility is the Web Content Accessibility Guidelines (WCAG). It is built upon four foundational pillars known as POUR:

  • Perceivable: Users must be able to comprehend the information (e.g. text alternatives for images, subtitles for video, high color contrast).
  • Operable: Every button, link, and input must be usable via keyboard alone without requiring a physical mouse.
  • Understandable: Clear error messages, logical reading order, and predictable navigation patterns.
  • Robust: Code must follow standard semantic syntax so assistive devices (screen readers, braille displays) parse it reliably.

2. The First Rule of ARIA

ARIA stands for Accessible Rich Internet Applications. It is a set of special HTML attributes that communicate additional semantics to screen readers.

💡 W3C Official Golden Rule of ARIA

"If you can use a native HTML5 element or attribute with the semantics and behavior you require already built in, then do so instead of re-purposing an element and adding ARIA."

Code Example 1: Native HTML vs Fake ARIA Buttons

html
<!-- TERRIBLE: Overengineered fake button (requires 10 lines of JS to fix tabindex, Enter key, Spacebar!) -->
<div role="button" tabindex="0" onclick="pay()">Pay Now</div>

<!-- PERFECT: Native HTML button has all keyboard and screen reader accessibility built-in for free! -->
<button type="button" onclick="pay()">Pay Now</button>
Key Insight: Native <button> elements automatically handle focus states, click events, Spacebar presses, and Enter key submissions with zero extra code. Never use <div role="button"> when <button> exists!

Code Example 2: The Accessible Icon Button (aria-label)

Icon-only buttons (like a magnifying glass for search or an "X" for close) have no visible text. A screen reader reading <button>🔍</button> would announce: "Button: Unlabeled". Use aria-label to give it an accessible voice:

html
<!-- 1. Search Icon Button -->
<button type="button" class="btn-icon" aria-label="Search all lessons">
  <svg aria-hidden="true" width="20" height="20">...</svg>
</button>

<!-- 2. Modal Close Button -->
<button type="button" class="btn-close" aria-label="Close dialog modal">
  <span aria-hidden="true">&times;</span>
</button>
Why aria-hidden="true" is used here: The visual "X" symbol (&times;) or decorative SVG icon would sound confusing if spoken aloud. aria-hidden="true" tells the screen reader to ignore the icon graphic and speak the friendly aria-label instead!

3. The tabindex Rules

The tabindex attribute controls how an element participates in keyboard Tab navigation:

Code Example 3: Tabindex Values Demystified

html
<!-- 1. tabindex="0": Inserts a custom element into the natural keyboard tab order -->
<div class="custom-card" tabindex="0">
  Keyboard accessible focusable card
</div>

<!-- 2. tabindex="-1": Removes element from tab order, but allows programmatic focus in JS -->
<div id="modal-heading" tabindex="-1">
  Dialog Title (JavaScript calls .focus() when modal opens)
</div>

<!-- 3. NEVER USE POSITIVE TABINDEX (tabindex="1", "2", "3")!
     Positive tabindex destroys the natural logical reading flow of the page! -->
The Golden Tabindex Rule: Only ever use tabindex="0" (to make something focusable) or tabindex="-1" (for programmatic JavaScript focus). Never use positive numbers!

Code Example 4: The "Skip to Main Content" Bypass Link

Keyboard users should never be forced to Tab through 40 navigation menu links on every page:

html
<!-- Place as the VERY FIRST element inside <body> -->
<a href="#main-content" class="skip-link">
  Skip to Main Content
</a>

<style>
  /* Hidden off-screen by default, slides into view when focused via Tab! */
  .skip-link {
    position: absolute;
    top: -100px;
    left: 10px;
    background: #2563eb;
    color: #ffffff;
    padding: 10px 16px;
    border-radius: 4px;
    font-weight: bold;
    z-index: 1000;
  }
  .skip-link:focus {
    top: 10px;
  }
</style>
How it works: When a sighted user visits the page, the link is invisible. But when a keyboard-only user presses Tab, the skip button slides into view, allowing them to jump straight past the navigation bar into the main article!

Code Example 5: Live Regions with aria-live

When content on the page updates dynamically via JavaScript (e.g., shopping cart total or live search count), screen readers must be informed:

html
<!-- aria-live="polite": Announces changes as soon as the user finishes current speech -->
<div id="cart-status" aria-live="polite" role="status">
  Shopping Cart: 2 items ($45.00)
</div>

<!-- aria-live="assertive": Interrupts the user immediately (strictly for critical alerts) -->
<div id="network-alert" aria-live="assertive" role="alert">
  Internet connection lost. Reconnecting...
</div>
Rule of Thumb: 99% of the time, use aria-live="polite" so you don't rudely interrupt the user mid-sentence. Reserve assertive for emergency warnings.

Code Example 6: Testing Accessible Name Computation in JavaScript

javascript
// Check what name a screen reader calculates for a button
const btn = document.querySelector("button");

// Accessible name calculation order: aria-labelledby > aria-label > inner text
const accessibleName = btn.getAttribute("aria-label") || btn.innerText;

console.log("Calculated Screen Reader Name:", accessibleName);
Accessibility Tree Priority: Browsers evaluate aria-labelledby first, followed by aria-label, and finally fall back to the visible text inside the element.
⚠ Common Beginner Mistakes
  • Removing focus rings with outline: none;: Never write *:focus { outline: none; } without providing a custom alternative focus style! Doing so completely blinds keyboard-only users who can no longer see where they are on the page.
  • Overusing ARIA roles: Writing <nav role="navigation"> or <button role="button"> is redundant noise. HTML5 tags already have these roles baked in.
  • Low contrast text: Gray text on a white background (like light gray #bbb on white) violates WCAG contrast minimums (4.5:1 ratio for normal text). Always check contrast!
💡 Pro Tips
  • Unplug your mouse for 15 minutes and navigate your website using only the Tab key, Enter key, and Spacebar. If you get stuck anywhere or can't see which link is highlighted, you have an accessibility bug to fix!
  • Test your pages with free built-in screen readers: Windows Narrator (press Win + Ctrl + Enter) or macOS VoiceOver (press Cmd + F5).
🔄 Quick Recap
  • Follow the WCAG POUR principles: Perceivable, Operable, Understandable, Robust.
  • Use native semantic elements (<button>, <a>) instead of fake ARIA divs.
  • Use aria-label for icon-only buttons with no visible text.
  • Hide purely decorative graphics with aria-hidden="true".
  • Only use tabindex="0" or tabindex="-1"; avoid positive tabindex.
  • Never remove focus outlines with outline: none without replacing them.
  • Use aria-live="polite" for dynamic UI notifications.

Hint: Add an aria-label attribute.

Exercise 2 (Medium): Decorative Image Masking Medium

How do you mark an SVG background pattern graphic so that screen readers skip it without announcing confusing garbage symbols?

Hint: Use the aria-hidden attribute.
Solution: Add aria-hidden="true" to the element:
<svg aria-hidden="true" focusable="false">...</svg>
Exercise 3 (Hard): Announcing Live Cart Updates Hard

You have a shopping cart badge reading "3 items". What ARIA attribute and value should you add to the badge element so that when a user clicks "Add to Cart", the new item count is announced politely by screen readers?

Hint: Look at aria-live.
Solution: Add aria-live="polite":
<span id="cart-counter" aria-live="polite" role="status">3 items</span>
