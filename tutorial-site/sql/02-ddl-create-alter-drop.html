🌟 Real-Life Analogy (10th-Grade Mental Model)

Think of building a house. DDL is the civil engineering and architecture phase. You decide how many rooms the house has, how thick the walls are, and where the doors are positioned (CREATE TABLE). If you decide later to convert the balcony into a bedroom, that is ALTER TABLE. If you demolish the entire brick structure down to bare soil, that is DROP TABLE. You cannot place furniture (data) inside a room that has not been built yet! Ghar banane ki misaal lein: DDL architecture aur civil engineering hai. Aap tay karte hain kitne kamre honge aur deewarein kahan banengi (CREATE). Baad me ek aur kamra banana ALTER hai. Poora makan bulldozer se tod dena DROP hai. Bina makan ka dhabba banaye aap andar saaman (data) nahi rakh sakte!

🗣️ How to Speak in an Interview (Crisp Speaking Points)
  • What is DDL? Data Definition Language consists of commands (CREATE, ALTER, DROP, TRUNCATE, RENAME) that define and modify the structure/schema of database objects rather than the data inside them.
  • TRUNCATE vs DELETE vs DROP (The #1 Interview Question!):
    • DROP: Removes table structure AND all data. Cannot rollback in most engines. Frees table space.
    • TRUNCATE: DDL command. Deletes all rows by deallocating data pages. Very fast, resets AUTO_INCREMENT counter, minimal transaction log generation.
    • DELETE: DML command. Deletes rows row-by-row with a WHERE clause. Fires triggers, logs every deletion, can be rolled back inside a transaction, does NOT reset AUTO_INCREMENT.
  • Auto-commit in DDL: In databases like MySQL and Oracle, DDL statements automatically issue an implicit COMMIT, meaning they cannot be undone via ROLLBACK. In PostgreSQL, transactional DDL is supported.
  • CHECK Constraint: Validates business rules at the database engine level (e.g. CHECK (age >= 18) or CHECK (salary > 0)).
  • Best Practice for ALTER in Production: Never run blocking ALTER TABLE ADD COLUMN ... DEFAULT 'val' on 100-million-row tables without understanding table locks!

1. What is Data Definition Language (DDL)?

In SQL, commands are classified into sub-languages based on their responsibility. DDL (Data Definition Language) is responsible for defining, altering, and destroying the structural blueprint (metadata) of database objects: tables, indexes, views, schemas, and constraints.

Unlike DML queries that insert or read user rows, DDL alters the internal catalog dictionary of the database engine.

2. The CREATE TABLE Command & Data Types

Every column in a table requires an explicit data type. Choosing the optimal data type minimizes memory footprint and dramatically speeds up cache utilization:

• Exact Numerics: INT (4 bytes, ±2.1 billion), BIGINT (8 bytes, for high volume IDs), DECIMAL(precision, scale) (for money/currency, avoids floating point drift).
• Strings: VARCHAR(n) (variable length up to n characters), CHAR(n) (fixed length, great for 2-letter country codes like 'IN' or 'US'), TEXT (large unbounded strings).
• Temporal: DATE, TIMESTAMP WITH TIME ZONE (always store UTC in production!).

3. Table Constraints: Enforcing Business Invariants

Constraints prevent corrupt data from ever touching your disk. Instead of relying solely on frontend forms or backend API validations, constraints are your impenetrable last line of defense:

• NOT NULL: Rejects missing/empty entries.
• UNIQUE: Rejects duplicates.
• DEFAULT: Automatically fills a value if the insert statement omits it.
• CHECK (expression): Ensures logical consistency (e.g., price > cost, discount BETWEEN 0 AND 100).

Practical Hands-On Code Demonstrations

Code Example 1: Creating a Production-Grade Users & Wallets Schema with All Constraints

sql
CREATE TABLE users (
    user_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(30) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL UNIQUE,
    age INT NOT NULL,
    is_verified BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    -- Check constraints enforce real-world business logic
    CONSTRAINT chk_user_age CHECK (age >= 13),
    CONSTRAINT chk_email_format CHECK (email LIKE '%@%.%')
);

CREATE TABLE user_wallets (
    wallet_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    balance DECIMAL(12, 2) NOT NULL DEFAULT 0.00,
    currency CHAR(3) NOT NULL DEFAULT 'USD',
    CONSTRAINT fk_wallet_user 
        FOREIGN KEY (user_id) REFERENCES users(user_id) 
        ON DELETE CASCADE,
    CONSTRAINT chk_positive_balance CHECK (balance >= 0.00)
);
• DECIMAL(12, 2): Up to 12 total digits with 2 digits after the decimal point (financial accuracy).
• CONSTRAINT chk_positive_balance CHECK (balance >= 0.00): Guarantees user balances can never go negative at the database level!

Code Example 2: Altering an Existing Table in Production (ADD, MODIFY, DROP Column)

sql
-- 1. Add a new optional column
ALTER TABLE users 
ADD COLUMN phone_number VARCHAR(20);

-- 2. Modify an existing column to increase length
ALTER TABLE users 
MODIFY COLUMN username VARCHAR(50) NOT NULL;

-- 3. Add a new unique constraint to the phone column
ALTER TABLE users
ADD CONSTRAINT uq_user_phone UNIQUE (phone_number);

-- 4. Drop an unused column
ALTER TABLE users
DROP COLUMN phone_number;
• ALTER TABLE allows non-destructive evolution of your database schema as business requirements change.

Code Example 3: TRUNCATE vs DELETE in Action

sql
-- Option A: Slow, transactional deletion
DELETE FROM users WHERE age < 18;
-- Scans rows, generates undo logs, triggers fire for each row.

-- Option B: Fast, nuclear table wipe
TRUNCATE TABLE users;
-- Instantly deallocates all data storage pages.
-- Resets AUTO_INCREMENT counter back to 1!
-- Cannot specify a WHERE clause.
• TRUNCATE is instantaneous because it does not iterate through individual rows; it resets the table's data page allocation pointer.

Code Example 4: Safely Dropping Objects with IF EXISTS

sql
-- Prevents scripts from crashing in deployment pipelines
DROP TABLE IF EXISTS user_wallets CASCADE;
DROP TABLE IF EXISTS users CASCADE;

-- Drop a specific index or view
DROP INDEX IF EXISTS idx_users_email ON users;
DROP VIEW IF EXISTS active_users_view;
• Using IF EXISTS ensures migration scripts can run idempotently without throwing fatal errors if the object does not exist.

Code Example 5: Renaming Tables and Columns Cleanly

sql
-- Rename column (ANSI SQL / Modern MySQL / PostgreSQL)
ALTER TABLE users 
RENAME COLUMN is_verified TO is_email_verified;

-- Rename the entire table
ALTER TABLE users 
RENAME TO app_users;
• Renaming preserves all existing constraints, primary keys, and data rows intact.

Code Example 6: Adding Foreign Key Constraints to Pre-existing Tables

sql
-- Add foreign key with explicit cascading rule after table creation
ALTER TABLE user_wallets
ADD CONSTRAINT fk_wallets_users
FOREIGN KEY (user_id) 
REFERENCES app_users(user_id)
ON DELETE RESTRICT
ON UPDATE CASCADE;
• ON UPDATE CASCADE ensures that if a user's PK ever changes, the wallet child table automatically syncs without breaking.

⚠️ Common Beginner & Production Mistakes
  • Using FLOAT or DOUBLE for financial amounts: IEEE floating point numbers suffer from binary rounding errors (e.g., 0.1 + 0.2 = 0.30000000000000004). Always use DECIMAL or NUMERIC for money!
  • Running TRUNCATE on a table referenced by foreign keys: Most database engines will reject TRUNCATE TABLE parent if child tables have active foreign keys pointing to it.
  • Confusing DROP and TRUNCATE: DROP destroys the table itself (it vanishes from schema). TRUNCATE leaves the empty table shell ready for fresh inserts.
💡 Senior Database Engineer Pro Tips
  • Always name your constraints explicitly: Write CONSTRAINT fk_orders_customer FOREIGN KEY... instead of anonymous FOREIGN KEY (...). When a foreign key fails in production, the database error message will tell you exactly which constraint failed!
  • PostgreSQL Transactional DDL: In PostgreSQL, you can wrap DDL in BEGIN ... ALTER TABLE ... ROLLBACK; to test dangerous schema changes safely without committing them!
⚑ Quick Recap & Key Takeaways
  • DDL defines and manages database schema structures (CREATE, ALTER, DROP, TRUNCATE).
  • TRUNCATE is a high-speed DDL command that clears all rows and resets identity counters without row-by-row logging.
  • DELETE is a DML command that removes specific rows filtered by WHERE and can be rolled back.
  • Constraints (NOT NULL, UNIQUE, PK, FK, CHECK, DEFAULT) enforce database integrity at the lowest level.
  • Always use DECIMAL for currency and TIMESTAMP WITH TIME ZONE for time data.

💡 Hint: Use CHECK (quantity >= 0) and CHECK (unit_price > 0).

Show Solution 
CREATE TABLE inventory (
    item_id INT PRIMARY KEY AUTO_INCREMENT,
    sku CHAR(12) NOT NULL UNIQUE,
    quantity INT DEFAULT 0,
    unit_price DECIMAL(8, 2) NOT NULL,
    CONSTRAINT chk_qty_non_negative CHECK (quantity >= 0),
    CONSTRAINT chk_price_positive CHECK (unit_price > 0.00)
);
Hard

Exercise 3: Suppose you need to delete all records from a 50-million-row audit log table. Compare running DELETE FROM audit_logs; vs TRUNCATE TABLE audit_logs;. Which one will you choose in production and why?

💡 Hint: Consider transaction logs (WAL/undo), lock duration, and time complexity.

Show Solution 
-- Choose TRUNCATE TABLE audit_logs;
-- Reasons:
-- 1. DELETE logs each of the 50 million row deletions individually in transaction undo/redo logs, causing disk bloat and potential database freeze.
-- 2. DELETE holds table/row locks for minutes or hours.
-- 3. TRUNCATE executes in milliseconds by simply freeing page allocations, generating minimal logs and resetting storage immediately.
